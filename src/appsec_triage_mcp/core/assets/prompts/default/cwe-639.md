## Object-level authorization audit

This finding is a static audit of one concrete HTTP endpoint. Review the handler,
the service it calls, and the repository or file sink that reads or mutates the
object. Trace every client-controlled object reference from path, query, body,
nested or batch input, filename, and token claims.

At each read, update, delete, export, batch, or file sink identify the trusted
authenticated principal and the owner or tenant predicate that binds the object
to that principal. Authentication, a route role, an unpredictable UUID, or a
client-supplied user ID is not object-level authorization.

Use `confirmed` only when exact grounded evidence shows a client-controlled
object reference reaches a sensitive sink without an owner or tenant binding.
Use `false_positive` only when the evidence shows every relevant object access
is bound to the authenticated principal or tenant. Use `unknown` when the
handler, service, repository path, dynamic dispatch, sibling verb, or policy
configuration is not visible. Name the missing file or function in
`blocking_question`.

Check sibling GET, PUT, PATCH, DELETE, export, and batch routes when the supplied
evidence shows them. Do not invent routes or runtime behavior. Never execute
HTTP requests or commands.
